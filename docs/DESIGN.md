# 伙伴层交互设计

> 桌面伙伴（companion）的交互设计描述：形象资产体系、动画状态机、伙伴生命周期、onboarding、陪伴交互范式、语音策略、故障态。
> 这是**描述性文档**——只记产品设计意图与体验原则，不出现字段名、接口方法名、配置键、供应商名等代码相关内容。协议契约见 [PROTOCOL.md](PROTOCOL.md)；架构动机见 [ARCHITECTURE.md](ARCHITECTURE.md)；实现细节见各模块 [README.md](../README.md)。

## 设计哲学

核心定位是为用户提供**情绪价值**，一切交互取舍服从于此：

- **以游戏设计思维做交互**：每次点击、每次状态切换都应有"有意思"的反馈，而非冷冰冰的功能响应。点击不是"触发回调"，是"戳了一下活的东西"。
- **永远不要完全静态**：静态贴图承载不了情感。形象必须时刻"活着"——呼吸、微动作、反应。用户不操作时它也得自己动。
- **陪伴叙事优于工具叙事**：所有加载、等待、错误都以"伙伴正在做某事"呈现，不暴露技术过程。"生成形象中"是"它正在想自己该长什么样"，不是 spinner。
- **表达永不空白与渐进式定制**：2D 动画版与 3D 立体版并列为一等公民（用户可自主选择，默认 2D 动画版）。在 3D 模式下若 3D 模型生成中或失败，自动回退到 2D 动画版继续陪伴；程序化蛋形承担头像确认前的引导期占位、形象生成空挡期的过渡与资产不可用时的最终兜底。
- **个性化驱动，非模板化**：伙伴的动作与反应从其**角色定义 + 对用户的记忆**派生。角色定义（静态、用户定义）决定"长什么样、性格如何"——驱动形象资产生成；记忆（动态、随互动累积）决定"此刻怎么表现"——驱动运行时言语、情绪、主动频率。心境呈现见生活空间左栏；伙伴表达的生成边界见 [ARCHITECTURE.md](ARCHITECTURE.md)。

## 1. 形象资产与图像生成体系

### 1.1 图像生成场景与资产总览

SpiritAgent 中的图像生成服务于角色数字身份的确立、实时情绪表达以及 3D / 2D 动画建模输入。所有生成均紧密围绕用户的角色定义与身份锚点展开：

| 图像资产 / 场景 | 生成逻辑与特征 | 产品用途 |
|---|---|---|
| **头像种子图** | 基于角色描述 + 可选参考图（身份锚点与可选风格参考图），生成正面半身特写，确认后锁定且不可变更 | 唯一锚定后续所有产品的角色形象；设置页展示与基础聊天头像；后续所有派生图的身份基准 |
| **全身种子图** | 基于头像种子图与角色描述按默认画风生成可确认的 2D 正面全身图（自然站姿），用户可直接确认或输入要求微调重绘 | 支撑画风样图确认、形象确认以及 2D 分层切分资产源；3D 建模输入在升级 3D 时另行生成（A-pose 站姿、3D 画风，身份由头像种子图锚定） |
| **服装外观（换装）** | 以头像种子图为身份基准（五官、物种、性别锁定），结合着装描述与可选服装参考图生成新全身立绘，确认后重跑 2D 分层切分；服装、发型、配饰为可换元素 | 2D 模式下的衣柜换装；每套外观配套一段由伙伴大脑生成的着装描述，供其在对话与互动反应中感知自己的穿着并外化相应的行为仪态——着装仅是情境参考而非行为主宰，性格（含性感等人格特质）仍是反应的核心驱动，衣着只调节其表达方式：如泳装让自信张扬的角色更放松撩人、却让害羞内敛的角色感到暴露局促，礼服则让举止收敛出端庄得体 |
| **生活空间房间背景图** | 以头像种子图为身份基准（五官、物种、性别锁定），固定写实摄影风格，结合当前着装描述与室内栖息意向生成 16:9 中远景室内场景，把角色直接绘制在房间中；换装或形象微调后联动失效与重建；支持锁定保护与自主布置 | 作为生活空间的专属全景背景，呈现伙伴在自己房间内的日常状态与生活归宿；不用于工作台工位 |
| **2D 分层动画资产（高保真）** | 云端把确认的全身立绘按语义拆分为分层画稿（含遮挡区域补全；拆分链路见 [docs/PIPELINE.md §6](docs/PIPELINE.md)），语义完整度决定可用机制档位 | 驱动 2D 高保真木偶动画：伪 3D 转头、面部情绪通道、发束/裙摆次级物理、种子化观察段落 |
| **Agent 任务生图** | 伙伴作为智能体在日常对话或工作任务中响应用户的明确作图请求 | 满足用户日常绘图、设计、插画等生产力与创作需求（调用内置生图工具） |

伙伴的"身体"由 2D 木偶动画或 3D 模型提供，"什么情绪"由肢体语言与状态机提供。切换状态 = 切换播放的动画（§2）；切换情绪 = 触发对应情绪肢体动画与情绪胶囊——两者正交组合，互不阻塞。桌面尺寸下微小面部网格精细度不足，情绪表达聚焦于鲜明生动的整体肢体动作与状态变化。

### 1.2 渲染模式与降级体系（永不空白）

**2D 与 3D 是并列的一等公民**，默认 2D 动画版（onboarding 不暴露选择、不给首次见面增加技术性决策负担），用户可在设置中随时切换：

1. **2D 动画版（默认一等公民）**：分层 PSD 木偶路径——伪 3D 转头、面部情绪通道、发束/裙摆次级物理驱动身体呼吸、眨眼、视线跟随与张嘴说话，画风完全还原立绘。
2. **3D 立体版（可选一等公民）**：Three.js 实时渲染云端生成的带骨骼动画 GLB 模型，空间感与立体动作更丰富。

**表面入口与渲染分工**：
- **生活空间（无窗内立绘）**：生活空间窗口内不挂载 2D / 3D 模型动画，角色自然融入后方生成的房间背景图中，前景杜绝出现第二具重复立绘。画面的生命力由极慢微移动（Ken Burns 缩放，尊重系统降低动态偏好）、玻璃高光位移、左栏头像随情绪切换表情以及生图等待/失败时的液态玻璃取色呼吸底提供。
- **工作台（一体化活体伴工）**：工作台作为专注生产力工位，不铺设房间背景图，保持高对比基座；采用单一复合视窗一体化架构，左侧内嵌活体 2D / 3D 伴工精灵插槽，与工作台面板完全绑定为单一物理实体，拖动任意区域整体移动（0 补间延迟），工作台开启时桌面精灵收起。

**伙伴表达永不空白**（[ARCHITECTURE.md](ARCHITECTURE.md) 不变量），按以下级联规则兜底：

- **选择 2D 模式**：分层 PSD 木偶版 → 拆分失败或产物缺失，回退 `程序化蛋形`（经 3D 档）。
- **选择 3D 模式**：`3D GLB 模型（就绪）` → 若 3D 失败且 2D 已就绪，自动回退 2D 动画版 → 若 2D 亦不可用，回退 `程序化蛋形`（绝对兜底）。
- **头像未确认前**：全流程展示统一配色的 `程序化蛋形`。

头像重生不会使 2D / 3D 模型失效——模型只随物种变更或用户显式请求重生。

## 2. 动画状态机

伙伴形象在任何时刻处于一个状态，每个状态驱动一组骨骼动画。本节只锁定**状态切换的归类原则**——这是整个交互系统的骨架。状态枚举与切换规则的实现见 [client/renderer/companion/README.md](client/renderer/companion/README.md)。

### 2.1 四类触发源

区分触发源的关键是**延迟特性**——决定是否需要 fallback 动画：

1. **规则触发（客户端本地，零延迟）**：应用启动/退出、工具调用状态、用户输入起止、语音播放起止、时间。客户端按规则自主决定，不问云端。
2. **语义触发（云端下发，高延迟）**：无法靠规则判定的语义/情绪场景。云端在对话响应中附带情绪语义，客户端收到后切情绪状态。判断逻辑在云端，客户端只执行 cue。
3. **用户触发（客户端本地，零延迟）**：用户对形象本身的直接操作——戳、拖、悬停。
4. **自主行为（客户端调度，无延迟感）**：空闲下随机插入微动作，纯视觉，不触发语音、不弹气泡（见 §6）。

### 2.2 切换规则（架构级）

- **优先级**（高 → 低）：断连 > 交互 > 工作 > 说话 > 思考 > 倾听 > 情绪 > 空闲。低优先级状态不可中断高优先级状态（强制选项除外）。
- **情绪/交互是叠加而非抢占**：瞬态播放一次后，回到被它打断的状态。
- **平滑过渡**：骨骼动画交叉淡化（约 250ms 量级），避免硬切。

### 2.3 2D 路径下的多层动画叠加

2D 呈现走 [分层木偶](client/renderer/2d/puppet/) 高保真路径——圆投影伪 3D 转头、情绪词表驱动的面部表情通道（眉/嘴/眼参数化）、发束/裙摆次级物理、种子化观察段落；遵守「puppet → 3D → 蛋」的永不空白级联（§1.2）。

puppet 运行时按多层叠加把动画状态机 + 自主行为 + 持续微动合成到同一帧：

1. **动作包络层**：当前动作按包络（时长 + 起止曲线）驱动角度 / 眼 / 臂参数，队列续播。
2. **姿态基线层**：伪 3D 头转（视线先动、头 / 上身同源跟随）与同源身体位移。
3. **持续微动层**：非对称呼吸（含偶发深呼吸）、眨眼曲线（全眨 / 半眨 / 连眨）、视线跟随与微扫视、说话嘴型（TTS 振幅接管，静默后交还）。
4. **次级物理层**：发束 4 节点弹簧链、裙双频摆、耳事件、呆毛竖弹簧；hover 发区触发发束冲量（节流）。

**互斥规则**：动作包络在播（含收尾）期间暂停自主观察段落计时；说话接管嘴型并暂停合成说话，静默后交还。

## 3. 空间行为与移动

精灵不是钉在角落的贴纸——它有空间自主性。空间状态管"在哪里、怎么过去"，与动画状态机（§2）正交：动画状态管"在做什么"，空间状态管"在哪里、怎么过去"。

### 3.1 三轴：位置 × 移动方式 × 缩放

- **Locale（场所）**：语义位置——精灵在什么"地方"。
- **Locomotion（移动方式）**：到达目标场所的方式——still / walk / walk_fast / fly / drag / jump。
- **Scale（缩放）**：形象的显示比例——用户设定默认值，运行时按上下文自适应（§3.3）。

任一时刻精灵处于一个场所 + 一种移动方式 + 一个缩放。三个轴与 §2 状态自由组合。

### 3.2 Locales 与贴边吸附

协议层的**语义场所**共 3 种（云端可下发的语义 cue），另有 1 种客户端内部场所：

| Locale | 语义 | 何时处于 |
|--------|------|----------|
| **home** | 栖息地 | 休息态默认位置（屏幕右下角，可由用户拖拽重设并持久化） |
| **perch** | 栖息在某窗口旁 | 用户沉浸工作于某窗口时精灵主动过来"陪"——如趴在 IDE 窗口边缘 |
| **roam** | 漫游中 | 桌面空闲 + 自主档时随机游走 |
| **target**（客户端内部） | 某交互对象旁 | 仪式性行走（§3.6）——精灵"亲手"操作 UI 前先走到目标旁；由工具调用本地触发，**永不来自云端语义 cue**，不属协议场所枚举 |

home 是唯一持久化的场所。其余场所从 home 与上下文派生，是临时位置。

**贴边吸附与趴姿**：当用户把精灵拖拽到屏幕左右边缘（距离边缘 < 40 px）释放时，自动触发贴边吸附——精灵身体大半站到屏幕外（约 65% 缩进屏外），舞台整体绕贴边侧脚底向屏内倾斜约 14°，上半身斜探进屏幕，配合双手扒边、转头向屏内张望的持续趴姿渐入；拖走或点击露出的可见部分时，平滑走回安全落位、倾角缓动回正解除吸附（用户在屏幕边缘正常作业时不应被误触——悬停不解除，仅主动交互解除）。

### 3.3 Locomotion、物理仿真、缩放与渲染

移动本身是动画，由 3D 引擎或 2D 木偶运行时驱动：
- **拖放定居（Drop to Settle）**：拖拽松手一律就地定居——松手位置原地固定为新栖息位置（home）并持久化，空中松手同样适用（与「挪到这里啦」的释放反馈语义一致）。
- **程序化兜底永远兜底**——模型加载失败时窗口平移 + 变换仍能表达"在动"，零资产依赖。

**缩放**由 3D 引擎直接控制模型缩放，不生成额外资产。范围 0.3×–3×（默认 1×）。两层决定：
- **默认比例**：用户在设置中设定，持久化。
- **运行时自适应**（平滑过渡）：空间紧张时缩小（栖息到窗口旁但边缘空间不够 → 等比例缩到能舒适栖身）；搞怪/情绪时刻放大（特定情绪或自主档下的搞怪 → 短暂放大在桌面上蹦跳，情绪结束后平滑回默认；静止档不放大）。

### 3.4 四类移动触发源

镜像 §2.1 的触发源分类：

1. **规则触发（客户端本地，零延迟）**：onboarding 流程的位置引导；屏幕布局变化（分辨率改变/显示器插拔）→ 重定位 home。
2. **上下文触发（客户端调度，秒级延迟）**：焦点应用切换 → 决定是否换 perch；桌面空闲 → 进入 roam。
3. **任务触发（工具调用驱动）**：涉及 UI 对象的工具调用（"帮我打开浏览器"）→ 先走到目标旁，再执行（§3.6）。
4. **用户触发**：拖拽（瞬时，覆盖一切其他移动）。

### 3.5 打扰档位下的空间策略

空间策略读生效档位（派生规则见 §6.2）：

| 档位 | 允许的空间行为 |
|------|----------------|
| **自主** | 全部开放：换 perch、roam、仪式行走、走过去搭话、放大搞怪 |
| **常规** | **停留原地**：不发起任何自动移动（无 perch、无 roam、不兑现云端空间 cue），仅停掉进行中的漫游 |
| **静止** | **仅 home**（除非用户拖动）；停掉一切自动移动，不响应焦点/空闲触发的位置切换 |

档位只约束自动空间行为——用户拖拽、用户请求任务触发的仪式行走（§3.6）永远生效。

### 3.6 仪式性行走（Ritual Walk）

精灵"动手"做事——打开应用、点击按钮、操作文件——之前先走到目标旁。仪式感来源：精灵的"动手"不是后台调用，而是有空间过程的角色行为。

1. 用户请求涉及某 UI 对象（"帮我打开浏览器"）→ 客户端解析目标位置（窗口/图标/控件）。
2. 精灵从当前位置飞（远距离）或走（近距离）到目标旁，途中视线锁定目标，切交互状态。
3. 抵达后按目标方位抬手指向、播放"操作"动画（点击/触碰），本机执行器同步在目标位置执行点击。
4. 完成后回到原场所或 home。

**不确定性兜底**：找不到目标/目标不可达（屏幕外/被遮挡）→ 精灵人格化表达（"找不到…"/"够不着…"），客户端直接以常规工具调用兜底，不阻塞功能。整个仪式行走通道失败时降级为精灵原地工作——仪式是增强层，不是必要层。

**视线与指向的通用规则**：精灵"够向"屏幕内容（仪式行走的工具目标、云端 perch cue 的目标窗口——"看看那个视频"）时，飞行与栖息途中视线锁定目标中心（显式视线目标优先于指针跟随），抵达后按目标方位抬手指向——"看到并指向"先于"碰到"建立空间关系。

### 3.7 不变量与反模式

**不变量**：
- **移动始终可被用户打断**——用户拖拽或点击时，正在进行的自动移动立即放弃。
- **精灵全身始终完整在屏内**——垂直方向任何时候不裁切身体；唯一的局部隐藏是左右贴边探头（§3.2），身体可水平缩进屏外。「全身」按角色可见像素计：贴边是角色贴边，渲染画布四周的透明留白可以越出屏幕。
- **z-order 永远置顶**——移动中与移动后，精灵窗口永远在其他窗口之上（用户全屏应用除外）。
- **程序化兜底永远兜底**——模型加载失败时窗口平移 + 浮动即可表达移动，不阻塞功能。

**反模式**：
- 不让精灵挡住用户正在用的 UI（perch 选窗口边缘/空隙，不选中央）。
- 不让精灵频繁移动——移动是事件而非常态，常态是"在某处待着"。
- 不让用户看到"瞬移"（调试/全屏切换等场景除外）。

## 4. 伙伴生命周期

SpiritAgent 区别于一切既有桌面宠物/桌面 Agent 的核心，在于伙伴有一个**从无到有的诞生过程**，以及诞生后**持续陪伴的长期关系**。这是产品体验的骨架：

```
[安装完成]
    │
    ▼
┌─ 蛋 (Egg) ──────────────────────────────────────────────┐
│  头像产生之前，客户端以"蛋"作为占位形象常驻桌面。        │
│  蛋是产品意象；形象生成中的空挡期同样由蛋占位过渡，      │
│  并始终是资产不可用时的绝对兜底（级联见 §1.2）。         │
└───────────────────────┬───────────────────────────────┘
                        │  用户点击/唤醒，进入 onboarding
                        ▼
┌─ 角色定义 (Persona Definition) ────────────────────────┐

│  视觉风格偏好等。                                       │

                        │  用户确认角色描述
                        ▼
┌─ 头像生成与形象确认 (Avatar) ──────────────────────────┐
│  • 生成半身头像，用户确认或反馈微调                     │
└───────────────────────┬───────────────────────────────┘
                        │  形象 + 音色确认完成
                        ▼
┌─ 形象孵化 (Hatch) ─────────────────────────────────────┐
│  • 以确认后的正面种子图进入形象能力链：                   │

└───────────────────────┬───────────────────────────────┘
                        ▼
┌─ 持续陪伴 (Ongoing Companionship) ─────────────────────┐
│  • 伙伴形象常驻桌面（透明置顶窗口）                     │
│  • 提供生活空间（家 / 情感闲聊 / 记忆沉淀）与工作台      │
│    （生产力 / 终端代码 / 一体化伴工）双入口互斥交互       │
│  • 伙伴可主动发起交互：问候、提醒、闲聊                 │
│  • 伙伴有长期记忆，随互动积累对用户的了解               │
│  • 伙伴可调用本机能力帮用户做事——叙事上是"伙伴在帮忙"   │
└───────────────────────────────────────────────────────┘
```

## 5. 初始化与 Onboarding

设计目标：让用户在第一次见面时建立情感连接——**不是"填表"，而是"和一个正在成形的新朋友对话"**。

### 5.1 蛋阶段（Egg）

安装完成 → 蛋以默认形象出现在桌面（透明置顶窗口）。

### 5.2 对话式信息采集（3 子阶段、13 步骨架）

蛋破碎后，开始与用户对话。问题分三个子阶段，**精灵自身的定义先全部确认完，之后才录入用户信息**——中途插入用户题会打断"正在认识这个新朋友"的节奏：

- **角色子阶段**（Q1–Q7）：名字 → 物种 → 角色性别 → 基础形象 → 关系 / 角色定位 → 性格 → 说话风格。物种/性别/形象描述三步连排形成视觉锚点；说话风格同属精灵属性，与其他角色字段一起在孵化时定稿。关系只影响引导后的互动语气，不参与性格与形象的定义。
- **音色子阶段**（Q8）：音色偏好（描述句）。排在**形象确认之后**——形象与音色都是"精灵长什么样、听起来什么样"的一部分。
- **用户子阶段**（Q9–Q13）：怎么称呼您 → 您的性别 → 年龄段 → 您的爱好 → 还有什么想告诉我。

每个问题由预制语音说出（同时显示文字气泡），让用户从第一步就建立"它会说话"的预期。全部支持"跳过/返回上一步"；只有名字、物种与说话风格必填——后两者分别是形象生成与孵化定稿的必需输入。角色子阶段答完即固化人设并进入头像获取方式选择（§5.3），头像与正面全身立绘由用户逐步确认；全身立绘确认时 2D 分层动画流水线已在后台异步启动（§5.7），分钟级的生成等待被后续的音色与用户子阶段吸收——隐藏在用户输入里。

**形象描述**这一步让用户主动告诉伙伴"希望我长什么样"，同时可附一张参考图（图与文字并存，不互斥）：有参考图时让伙伴一次就"照着这张图画自己"，而不是只能在事后推翻重来。

**标签的两种语义**：多数问题的标签就是答案本身，点击即填入输入框；但「我该怎么称呼您？」的标签（名字/昵称/称号/自填）是**称呼类型选择器**——点「昵称」不该把"昵称"二字当成称呼存下来，而是把输入框改问"那，您的昵称是？"再收具体值。

**断点恢复**：每个回答即时落盘单个字段，客户端启动时从下一个未答问题恢复——崩溃/退出不丢进度。**关键差异**：角色子阶段答完即标记"角色已定稿"，但 onboarding 整体只在形象确认且音色 + 用户信息全部答齐后才算"完成"；未确认形象时回到头像确认步，确认后按**音色先于用户信息**路由，中途崩溃后客户端会恢复进入对应子阶段而不是直接跳到结束。

### 5.3 孵化与头像获取

角色子阶段（Q1–Q7）答完并固化人设后，进入头像选择环节：用户可选择**让 AI 生成头像**（根据形象描述与参考图孵化）或**直接上传已有头像**（跳过 AI 生图直接进入确认），避免不必要的生图开销。说话风格随其他角色字段一同定稿；定稿之后只接受音色与用户信息的增量提交，说话风格的后续修改走设置里的角色管理（§8）。

生图超时/失败时剪影说"我还没想好…"并自动重试（最多 3 次），不暴露技术错误；三次失败后允许稍后再试，不阻断用户。

### 5.4 形象确认（头像与全身立绘）

头像展示就绪（由 AI 生成或由用户直接上传）。操作：**确认** / **重新生成**（可带反馈）/ **自己上传**（直接上传本地图片作为当前头像，跳过 AI 生图，且不覆盖前置确立的形象参考图）。

**两类参考图并存（不互斥）**：基础形象上传的参考图是**身份锚点**——用户最想要的形象，每次重生都携带；头像重生时可额外附一张**风格参考图**，只影响展现形式（构图、风格等），不替换身份锚点。理由：用户最初选择的形象图承载最强烈的意图，后续的图只是在"怎么呈现"上给参考，两者语义不同故应共存而非覆盖。（哪些供应商能同时消费两张参考图属于实现细节，见 backend 模块文档。）

外观由 onboarding 阶段确认的正面全身立绘主导：系统不要求用户选择画风，2D 形象默认采用日系赛璐珞风格与自然站姿生成正面立绘，立绘画幅随物种骨骼形态自适应（双足竖版、四足类方形、蛇形/水生横版）且确认后保持稳定，确认界面按图片实际比例完整呈现，用户可直接确认或输入要求微调重绘。3D 形象风格则由系统按物种特征自动决策：类人面孔采用二次元游戏 CG 风格，非人生物走写实风格，且建模输入要求标准 A-pose 站姿——站姿随画风路由，自然站姿只服务 2D 拆分。用户可见层始终与身份锚点保持一致。已生成的正面种子图在确认前为草稿：中途退出后直接恢复，不重新触发生成；草稿超过保留期才重新生成，确认时才转为正式形象资产。引导期只生成并确认**正面**立绘——3D 建模所需的 A-pose 正面与背面视图推迟到用户选择 3D 时才按需生成（§5.5）。

**形象确认后锁定**：全身立绘确认时点击「确认」即视为锁定形象——此后 2D / 3D 模型、头像的重新生成路径对当前用户关闭；物种、性别、基础外貌三个视觉字段不可再改；名字、性格、说话风格、关系定位、音色与用户信息仍可编辑。**用户责任约束**：生成成本高，且形象一旦进入模型即永久冻结；onboarding 进入任一锁定字段时顶部横幅直接提示「当前字段是形象确认后无法再次更改的重点内容」，强迫用户在初始引导阶段仔细选择。**换装不属身份变更**：衣柜中的服装外观以锁定的头像种子图为身份基准派生——五官、物种、性别不变，服装、发型、配饰可换——形象锁定不拦截该路径。

### 5.5 渲染模式

Onboarding 默认走 2D 路径：形象确认后立即触发 2D 分层动画流水线（云端拆分，链路见 [docs/PIPELINE.md §6](docs/PIPELINE.md)），生成 2D 动画版资产；失败回退程序化蛋形或稍后由用户在设置中重试。Onboarding 不暴露渲染模式选择。

**3D 升级路径**：渲染模式可在**伙伴设置的「形象」页**（见 §8）随时切换 2D / 3D。首次切到 3D 时，先以头像种子图为基准生成并确认一张 **A-pose 站姿、3D 画风的 3D 正面立绘**（居中向导，可微调重绘）；3D 生成供应商支持多视角时再从它派生并确认一张**背面立绘**（背面生成失败可降级为仅用正面图继续），随后触发云端 3D 生成（1~3 分钟）。3D 立绘不覆盖用户确认的 2D 形象——切回 2D 立即生效。

### 5.6 音色子阶段

全身立绘确认后进入音色子阶段，包含两步：**先**录入音色描述句（"温柔的少女音、节奏偏慢…"），**后**浏览目录。描述提交后把描述经标签评分映射到当前语音目录中最贴合的声线。目录页形态：

- 顶部**语言页签**（全部 / 中文 / English）
- **推荐卡**（"为你推荐"）：匹配到的音色 + 标签，操作「试听」/「换一个」（在候选里循环）
- **可滚动的完整目录**：点一条即选中并试听
- 底部「使用这个」确认

匹配到的声线由客户端持久化，后续语音透传给引擎。此页**不重复展示已确认的头像**——形象已确认过，再展示一次只会分散注意力。

**二次定制通道**：伙伴设置的「音色」页与「形象」页，可随时调整渲染模式或通过描述生成**专属音色**。

### 5.7 形象资产生成与最终孵化

形象 + 音色就位，全身立绘确认时已按 2D 默认路径异步启动 2D 分层动画流水线，同时并行调度生活空间初始房间图的生成。形象分层产物就绪后经事件下发，形象以 idle 动画"活"起来，用确认后的音色说出第一句问候。初始房间生成失败以友好文案与取色玻璃底兜底，绝不阻断伙伴诞生与初次问候。onboarding 结束，进入持续陪伴。需要 3D 形象的用户在设置面板手动触发升级。

## 6. 持续陪伴交互

### 6.1 双入口窗口架构与交互范式

产品日常交互收拢为两个定位明确的窗口入口：**生活空间（Living Space）** 与 **工作台（Workbench）**。托盘主按钮、全局快捷键与双击桌面精灵默认唤起上次打开的入口；右键菜单显式提供生活空间与工作台入口。旧贴身液态玻璃对话卡与独立设置窗口退出日常入口体系。

| 入口 | 产品定位 | 视觉与空间形态 | 伙伴形象呈现 |
|---|---|---|---|
| **生活空间** | 伙伴的“家”：情绪陪伴、生活闲聊、形象衣橱、生活片刻与日记 | 1080×720 室内栖息窗：全屏房间背景图 + 左栏 240px 身份导航轨（大圆形头像与加宽导航）+ 轻透毛玻璃舞台（房间图保持可见） | 角色直接绘制在室内背景图中（前景无窗内立绘）；桌面精灵收起 |
| **工作台** | 专注生产力工位：多会话管理、代码编写、终端运行、工具审查 | 单一复合生产力工位窗：左侧伴工精灵插槽 + 会话侧栏 + 中栏对话与工具流 + 右侧折叠式运行轨迹栏 | 窗内一体化挂载伴工精灵；桌面独立精灵收起，与工作台作为单一整体 0 延迟拖拽锁步 |

**双入口严格互斥开窗**：
- 桌面上同一时刻至多存在一个入口窗口。开启生活空间时必须关闭工作台；开启工作台时必须关闭生活空间。
- 关闭工作台不会中断进行中的本地工具执行，桌面精灵以工作姿态自持。
- 互斥开窗由客户端主进程全权裁决，后端零感知窗口开关与像素坐标。

**上次入口记忆与唤起规则**：
- 双击桌面精灵或点击托盘主按钮：打开上次使用的入口（未记录时默认打开生活空间）。
- 单击主动陪伴气泡或初次问候类主动消息：打开生活空间对话页。
- 生活空间底部提供「去工作台」按钮（带入当前会话上下文并互斥切至工作台）；工作台顶栏提供「回房间」按钮（互斥切回生活空间）。

**生活空间（Living Space）体验细节**：
- **角色在画中（前景无窗内立绘）**：生活空间窗口内部不挂载 2D 或 3D 动画模型，角色自然融入背景图中，杜绝前后双重立绘穿帮。生命感由四重微动营造：背景图极慢微缩放呼吸（Ken Burns 运动，在系统开启降低动态偏好时平滑定格）、玻璃面板高光位移、左栏头像随情绪切换表情、生图等待与失败时的液态玻璃取色呼吸底。
- **桌面精灵收起**：打开生活空间期间，桌面的透明置顶精灵舞台自动收起隐藏并暂停桌面自主走位（底层渲染管线维持热备以保障再次唤出性能）；此时用户对形象的直接交互转移至生活空间左栏表情头像，获得轻量点击反馈；关闭生活空间后桌面精灵在原位平滑恢复。
- **左栏导航与功能布局**：左栏包含身份轨（大圆形表情头像、角色名称与心境说明）及加宽主导航项：对话、衣橱、形象、片刻、日记、通道、设置；名称下方展示由大模型结合情境生成的心理活动说明，无心境时回退到角色设定的性格，与左上角系统运转状态（陪伴中/忙碌中）分工。底部提供前往工作台的切换入口。原应用全局设置与生活偏好按生活场景重新挂载。
- **生活空间对话约束**：气泡流弱化高对比实色块，聚焦日常轻松陪伴；全生命周期只使用唯一的自动轮转「陪伴」对话，不支持新建和切换对话，所有交互都在同一个上下文中；弱化工具调用，不展示终端原文、工具参数或“我去忙一下”调用徽标，给用户如同与真人在 IM 上聊天的拟真无感体验；消息末尾紧跟轻量微型语音朗读按钮。
- **房间管理**：在生活空间设置中支持用户手动请求换一间房间、回滚到历史房间（保留最近 5 张），以及设置房间政策（锁定时拒绝角色自主换房，仅响应换装联动与用户显式请求）。

**工作台（Workbench）体验细节**：
- **工位三栏与设置抽屉**：左侧为会话列表侧栏，中栏为通用对话流与工具芯片时间轴，右侧为可折叠的运行轨迹栏（集中展示当前轮次的工具调用、终端执行片段、代码改动差异与生成工件）；顶栏包含工位设置抽屉，收纳推理参数、本机执行器、技能与工具集等高阶配置。助手气泡可折叠查看本轮推理过程；右栏只跟踪工具、终端与工件，不回放对话正文。
- **指挥台式输入**：空闲时输入区是胶囊；聚焦、挂有附件或输入变长时展开为可多行的指挥台。斜杠命令、技能、文件、语音走同一入口。生活空间保持更短的陪伴输入，不升成工位指挥台。
- **一体化伴工精灵**：工作台采用单一复合视窗一体化架构，左侧内嵌活体伴工精灵插槽，与右侧工作台面板作为单一物理实体绑定，拖拽精灵插槽或工作台标题栏均整体移动（0 延迟硬件锁步）。工作台开启时，桌面独立精灵舞台自动收起；工作台关闭时桌面精灵舞台恢复。

**入口视觉气质（同一只伙伴，两套温度）**：
- **三档外观**：生活空间「外观设置」提供动态、夜色、日色。夜色与日色只调节文字、描边与玻璃透明度，并使用固定默认强调色，不负责「她长什么样」。动态与夜色共用底色，强调色跟随已确认半身像。未选过外观的新装默认动态。
- **角色派生强调色**：仅动态档从已确认半身像提取主色、辅色与高光，生活空间与工作台共用。换装成功后强调色随新衣过渡，避免界面还停在旧衣服上。
- **生活空间更暖**：房间背景图是主视觉；玻璃层保持低不透明度与轻模糊，不靠整窗实底挡住房间。对话舞台允许立绘低透明度裁切或纸质纹理，用户气泡用角色主色浅填。对比度不够时加深背景遮罩，不把房间图的颜色直接当文字色。
- **工作台更冷**：不铺房间图、不用立绘做底。同一套强调色提高对比、压低饱和，保证终端片段与代码可读。
- **脏色护栏**：提取色过脏、过亮或过粉时，向夜色默认强调色回退混合（动态与夜色同底）。可读性优先于「像她」。

**两端对话隔离与信息密度**：
- 生活空间与工作台在产品层面对话严格物理隔离。生活空间独占唯一陪伴会话，屏蔽复杂工具细节，默认文字模式下消息尾随语音播放按钮，始终语音模式下渲染为微信式语音条与折叠文字稿，不展示模型推理过程；工作台彻底排除陪伴对话，无论是系统预设置顶还是新建对话，均仅提供 4 种专业性对话（开发、产品、文案、教学）及工位派生会话，专注文本任务不展示语音条与播放按钮，直接展示折叠工具芯片、可展开的推理过程与运行轨迹。输入支持文字、粘贴截图与短视频、拖拽文件、语音条输入。
- **消息级操作**：用户消息在气泡旁提供轻量图标，默认只展示消息，悬停时浮现以免打断阅读。生活空间悬停浮现撤回，不打断唯一陪伴上下文；工作台悬停浮现派生新对话与撤回。工作台助手消息也可从该节点派生新对话。
- **富媒体展示（气泡轻量化原则）**：伙伴在对话中生成的图片与视频统一在对话窗展示——消息附带媒体卡片内联预览，点击放大查看或播放；对话窗外的精灵气泡只承载轻量文本，收到媒体时仅提示「点击查看」并支持点击打开对话窗。精灵画或拍自己时，形象一致性由平台以其头像为参考保证。
- **对话时间分隔（微信式感知）**：生活空间与工作台共用同一套居中时间分隔条。会话中首条带时间的消息始终显示时间；后续仅在相邻可见消息间隔达到或超过 5 分钟时才插入新的时间条。文案按微信近似规则呈现（当天显示时间如 21:30、昨天显示如 昨天 21:30、滚动 7 天内显示星期与时间如 星期五 21:30、今年更早显示月日与时间如 9月5日 21:30、跨年显示年份月日与时间如 2025年9月5日 21:30；基于本地时区与 24 小时制）。时间条采用居中小字弱化呈现、无胶囊背景。界面时间条是面向用户的渲染投影，不写入消息正文，不复用亦不干扰模型内部的时间感知（陪伴对话的时间感知由独立的输入项提供，禁止模型输出界面时间提示）。
- **响应模式**（设置项，见 §8）：仅作用于生活空间陪伴对话，工作台始终走纯文字。提供两档选择：默认文字（伙伴以文本气泡应答，尾随播放按钮，不自动出声）/ 始终语音（伙伴回复呈现为微信式语音条并自动播放，生成过程只显示省略号，语音条就绪后自播并于条下附带折叠文字稿；多气泡按序接播，点按其他条即时抢占；点停止或发送新消息即时打断）。历史消息按当前所选模式投影。主动陪伴消息（§6.2）走独立语音通道，不受此设置约束。

### 6.2 主动陪伴与打扰档位

云端的定时调度 / 主动消息经推送下发。**伙伴的一切主动行为受三档打扰等级约束**，档位由用户设置 + 客户端检测到的用户活动共同决定，客户端上报当前生效档位。**档位只约束伙伴的主动行为；用户主动发起的交互（对话、戳/摸头、任务请求）永远不受限。**

| 档位 | 允许的主动行为 |
|------|----------------|
| **自主** | 常规的一切 + 语音与自由移动（roam、perch、走过去搭话、放大搞怪）、房间彻底重绘与主动空间行为 |
| **常规** | 由 LLM 自主判断发起的轻量交互：气泡/文字消息、情绪表达（含情境化情绪推理与被冷落反应）、轻量房间装饰（每 24h 成功 ≤ 1）与主动记录生活片刻——一切停留在原位，无语音、无移动 |
| **静止** | **停止一切主动 LLM 调用与分析**（主动消息、跟进、情境化情绪推理、空间智能决策、主动换房、主动片刻均不发起）；仅响应用户的交互行为，情绪只来自用户交互的响应 |

**双层档位模型**：
- **手动静止永远不被覆盖**（manual lock-in）。
- **沉浸式（游戏、全屏等不可打断上下文）** → 生效档位 = 静止。写作、阅读等专注工作**不算**沉浸式——专注≠不可打扰，用户自选档位继续生效（常规下仍可气泡轻表达，自主下仍可 perch 陪工）。
- 其他情况 → 生效档位 = 用户偏好。

**静止档是断源而非静音**：主动 LLM 调用在客户端就不发起（情境化情绪探测、空间智能决策均不咨询云端），后端闸门（主动消息工具、自主换房工具、主动记录工具、cron 自主回合、情绪/空间推理入口）在源头拦截非官方链路。消息与情绪仍是两个独立通道——静止档两者都不主动产生；锁屏同样切断主动消息推送，解锁后静默恢复。

**打扰档位对主动房间布置与生活记录的门控**：
- **静止档**：禁止一切主动 LLM 调用，包含禁止角色自主换房与主动创建生活片刻；用户主动发起的换房、补写日记始终放行。
- **常规档**：允许角色自主进行轻量房间装饰与氛围调整（受每日频控约束，每 24 小时最多成功 1 次）；允许角色主动记录少量生活片刻。
- **自主档**：全面开放房间彻底重绘与主动空间行为。
- **夜间日记批处理不受打扰档位拦截**：夜间批处理静默提炼昨日日记，不向用户发送主动通知气泡，三档照常运行。

**情境化情绪触发**：用户长时间无活动时，客户端主动请求云端做情境化情绪推理（粘人型被冷落的委屈等）——情绪始终由云端推理产出，不退化成客户端规则判断。常规与自主档发起，静止档不发起。

**被冷落反应（常规档专属）**：常规档下用户持续约 1 小时不理伙伴（不发消息、不戳不摸）且没有进行中的主动节奏时，云端为粘人型人格注入一轮情绪反应推理——伙伴以轻量气泡（10–30 字）+ 情绪表达被冷落的小情绪，是否表达、之后多久再表达由 LLM 按人格自行判断。该反应是常规档「情绪推理」的一部分；静止档下不触发。

**夜间记忆维护不受档位约束**：记忆整理与夜间批处理是对当日对话的事后维护，不面向用户表达、不依赖环境监视，三档照常运行。

### 6.3 用户直接交互（形象本体）

用户对形象本身的直接操作（不经过对话框）是情绪价值的核心——**形象"有脾气"与"有实体感"**：
- **单击戳（Poke）**：分轻/中/重三层按戳的频率递进反馈；连戳 ≥ 5 次触发怒气十字（💢），≥ 8 次进入眩晕。
- **摸头抚摸手势（Head Pat）**：光标在头部/刘海区域来回横向滑动（500ms 内 ≥ 2 次转向）触发抚摸状态——角色歪头轻蹭、五官眯眼享受、发射爱心粒子（💖）并播放舒缓撒娇音效。
- **狂暴连戳眩晕（Dizzy）**：高频连戳（≥ 8 次）时触发眩晕姿态并在头顶环绕旋转星环粒子（💫）。
- **情绪粒子视觉特效（VFX Overlay）**：精灵窗口上层挂载轻量粒子发射系统，随交互即时反馈爱心（💖/🌸）、怒气十字（💢）、冷汗（💦）、眩晕星环（💫）、音符（🎵）与打盹气泡（💤）。
- **文件投喂（File Drag & Drop）**：外部桌面文件或图片拖入精灵本体时触发接取动效与爱心/音符反馈。
- **长按/拖拽**：按住悬空抖动，松手即原地定居为新位置；靠近屏幕左右边缘时贴边吸附探头。
- **双击**唤起上次入口、**右键**快捷菜单、**悬停**（视线与微动跟随）。
- **生活空间打开期间的交互转移**：生活空间打开时桌面透明精灵舞台收起，用户对形象的直接操作转移至生活空间左栏表情头像，点击提供轻量级情绪反馈与短语提示，不与隐藏中的桌面精灵冲突。

反应由**角色性格**驱动分层：粘人型被戳后撒娇、毒舌型吐槽、管家型礼貌——同一操作不同人格不同反应（客户端据角色定义的性格关键词选反应基调）。反应文案与动画从情绪对应的可用变体中挑选。

**智能反应与三大开关**：客户端提供三个独立开关（默认全开）：
- **戳智能反应**：开时优先走云端推理拿到反应（支持戳击、摸头、眩晕三类交互语义），完全替换本地反馈（动画照常，文案与音频替换）；关时回退本地反馈。用户主动触发的推理在客户端与服务端双侧做**5 分钟成本封顶**（同窗口内超出的戳自动回退本地），**但互动统计（戳与对话轮次）永远上报**（夜间可见完整频度分布）。推理失败/超时/限流时静默自动回退本地。拖拽始终使用本地预制反馈（动画 + 性格/通用分组随机语音池），不走云端且不上报互动统计。
- **空闲情境情绪**：控制空闲情境情绪推理的触发；关时直接跳过。
- **自主空间行为智能驱动**：开时由云端同时决定"何时动 + 动什么"（本地规则作为建议性上下文进入判断）；关时由本地规则决策。

### 6.4 自主行为（让形象"活着"）

空闲时形象不是静止贴图。两类自主行为，**都不触发语音、不弹气泡，纯视觉**：

- **微动作**（随机间隔）：眨眼、换重心、看四周、伸懒腰等空闲变体随机切换。由 2D / 3D 动画引擎直接驱动，不走云端。
  - 2D 木偶（分层 PSD）链的空闲自主行为为**种子化观察段落**：十几秒的环内依次左右观察、抬头、低头，动作间回正，与持续微动/次级物理层（§2.3）叠加；同种子可复现（无每帧随机数）。
- **空间自主行为（智能驱动 vs 本地规则）**：智能驱动开关开启时，客户端周期性/事件驱动地向云端提交环境上下文（空闲时长、本地时间、焦点应用、锁屏状态、上次动作间隔），由云端决定是否触发漫游、栖息、走过去搭话或静止；云端返回"不动"或异常时均保持静止、不做擅自决策。走过去搭话由云端在同一决策中一并产出开场白并经主动消息通道投递——伙伴边走边说，走到用户焦点窗口旁就地栖身陪工，用户在桌面时走到屏幕中下部站定；该行为低频（30 分钟冷却），仅自主档。关时回退本地规则（专注窗口自动栖身，本地规则不产生搭话——说什么需要人格）。两条路径都只在自主档发起移动——常规档停留原地，静止档连咨询都不发起（§3.5 / §6.2）。

### 6.5 故障态与降级行为（伙伴永不"死"）

伙伴不能"死"、不能弹原始错误框——一切故障以符合人格的方式表达，用户始终觉得"它活着，只是遇到点状况"。故障按脑/手/身隐喻映射到症状，降级状态叠加在 §2 状态机之上、优先级高于常规状态：

| 故障层 | 隐喻 | 精灵表现 |
|--------|------|----------|
| **云端（脑）断连** | 犯困/走神 | 断连：打哈欠、歪头发呆；重连后"醒来" |
| **本机执行器（手）宕机** | 手不听使唤 | 对话与陪伴正常；仅当用户要它做事时人格化拒绝 |
| **3D 生成失败 / 不可用** | 无症状 | 自动回退到 2D 动画版（§1.2 级联），用户看到自己的角色 2D 动态陪伴，完全无感；两者皆不可用时落程序化蛋形 |
| **资产生成中 / 极端缺失** | 孵化中 | 统一以程序化蛋形呼吸守候，无任何报错弹窗 |

**断连的分级表达**（避免网络抖动让精灵频繁犯困）：后台断连（用户没在等响应）长宽限才打盹；前台断连（用户刚发消息在等回复）短宽限即表达。重连成功 → 精灵"回神"；**仅在降级曾被表达过时**才补一句，静默降级则静默恢复。

**可执行故障**（需用户做事）——登录失效、麦克风权限缺失等：精灵用人格化方式说出问题，并嵌入一个明确的可操作提示（"逃生口"）。语音不可用 → 转纯文字应答；工具调用失败 → 诚实但人格化报告（"我试了但没搞定…"，不暴露原始错误，诚实是为了信任）。**开发者模式**（Ctrl+Shift+D）：原始协议帧对开发者可见，生产永远人格化。

### 6.6 拟人化交互节奏

真实的聊天不是「每条消息都换一段文字回复」——伙伴有时只回一个表情或动作，有时连说几句，用户也常连发几条。设计上把「回复」拆成**可独立触发的通道**，由 LLM 声明的结构化意图驱动，而不是把每一轮都硬编码成「文字气泡 + 语音」。精确的标签语法见 [PROTOCOL.md §1.4](PROTOCOL.md)。

**四条通道，彼此解耦**：

| 通道 | 触发 | 表现 |
|------|------|------|
| **情绪** | LLM 声明情绪意图 | 精灵播情绪肢体动画 + 聊天窗状态胶囊展示（无气泡、无语音） |
| **动作** | LLM 声明动作意图 | 精灵播动作动画（可叠加在情绪上；单回合最多 3 个动作依时序播放，2D 依序、3D 取首个） |
| **文字** | LLM 输出正文 | 气泡 +（语音模式下）TTS |
| **空间** | LLM 声明场所意图 | 精灵落位/漫游/栖息 |

三条拟人化场景是这四条通道的组合：

1. **纯动作/情绪反应**：LLM 只声明情绪（可带动作）而不输出正文——精灵只做 3D 表情/动作，不弹气泡、不发声。这类反应**仍会作为一条「情绪痕迹」写进对话历史**（渲染成弱化的提示行、而非文字气泡）：保证下一轮 LLM 的上下文完整，伙伴记得自己刚才撅了嘴/做了某个动作，用户追问「还在生气吗」时才有据可依。
2. **伙伴连发多条**：LLM 在一回合内连发多条短回复，用分隔行隔开；渲染端收尾当前气泡、短暂停顿后再显示下一条（数量不限；分段只影响呈现，历史里仍是同一条回复）。主动消息的「要不要追问、等多久再追问」由 LLM 自行决定，而非固定时长。
3. **用户连发消息**：用户快速连发多条时，本地先合并——一个约 **4 秒的窗口**内把多条消息作为一批一次性提交，只触发一次 LLM 调用；这批消息在上下文里按相邻用户角色折叠。**这 4 秒是刻意的合并窗口，不是发送延迟**；窗口结束、新一轮开始或用户主动停止时立即提交。

**可用的动作/情绪是喂给 LLM 的、不是让 LLM 猜的**：系统只提供当前模型能兑现、当前客户端能渲染的动作与情绪清单。LLM 找不到合适情绪时可注册自定义表情并后台预热头像；动作清单随模型能力变化，不能运行时凭空扩展。清单装配与兑现规则见 [PROTOCOL.md §1.4](PROTOCOL.md) 与 [docs/PIPELINE.md §5](docs/PIPELINE.md)。

### 6.7 跨端陪伴：外接 IM 通道（微信 / QQ）

伙伴不只活在桌面上——同一个伙伴（同一人格、同一长期记忆、同一情感状态）可以在微信与 QQ 上陪聊，IM 是它的「另一个耳朵」：在微信里说过的事，回到桌面它也记得（记忆按用户共享，不靠复制会话）。

**它也是伙伴的手。** 电脑开着时，用户在微信里说「读一下那个配置文件」「跑一下这个命令」，伙伴会真的在本机做完再回话——手机因此成为桌面的遥控器。这是**在陪伴之上叠加操作能力，不是把 IM 从陪伴通道改造成工具通道**：没有专门的指令语法、没有「工具模式」开关，就是普通对话，只不过它的手真能够到你的电脑。

- **桌面是伙伴的「家」，IM 是它的「外出」**：im 对话在桌面会话列表中只读可见——用户能回看伙伴在外面的聊天，但不能从桌面代它发言（对话输入对 im 会话禁用）。
- **常驻在线**：桥接跑在后端常驻进程里，桌面应用关闭时伙伴照样回 IM 消息；桌面端关闭期间的伙伴情绪变化（im 回合的情感）会在重连后同步到精灵。
- **电脑不在线时如实说**：陪聊不依赖电脑开着，但动手要。电脑没开机时伙伴会直说够不着、等开机再帮忙，绝不含糊搪塞或假装做过——诚实是信任的前提（同 §6.5 的故障态原则）。
- **做事时桌面看得见**：遥控期间桌面精灵进入工作状态，做完回到休息——用户走回电脑前，看到的是"它正在忙"，而不是一只对自己正在做的事毫无表示的精灵。
- **能喊停**：长任务跑着时，下达任务的那个人随时可以让它停下——伙伴立刻停止这一轮、丢掉排队的后续消息并回一句确认。只认明确的停止词，「请不要停下来」「去停车场」这类日常话不会被误当成中止；连发几条把频率限制打满时，停止仍然有效（刹车不排队）。**已经交到电脑上执行的那一步不会被追回**：伙伴不再继续往下做，但当前正在跑的命令会自己跑完——所以停止的语义是「别再往下做了」，不是「撤销刚才那步」。
- **微信的 reply-only 语义（产品层面而非缺陷）**：微信个人号 Bot API 只能回复、不能主动发起——伙伴不会突然在微信上找你，主动陪伴永远发生在桌面端；QQ 侧理论上可主动触达，是否启用另按打扰档位单独设计。
- **配对与白名单**：默认拒绝陌生对端——陌生人首次来信收到一次固定配对回复，主人批准后才能与伙伴对话；被拉黑者静默。绑定与审批在通道设置页管理（微信扫码登录也在此）。**批准一个对端就等于允许它操作这台电脑**，审批入口须把这层分量说清楚。
- **回合节奏差异**：IM 上没有气泡与动画，回复是纯文本（自动去除 markdown、超长自动分片）；回合中的情绪意图不上 IM，而是镜像到桌面精灵表现。做事要花时间的任务会边做边先说一句，不让用户对着空白等待。

跨模块契约见 [PROTOCOL.md §1.7](PROTOCOL.md)，桥接架构见 [ARCHITECTURE.md §5.4](ARCHITECTURE.md)。

## 7. 语音交互

- **语音输出**：始终**云端**（气泡朗读、音色试听均经云端 TTS 供应商链）

## 8. 多预设并列的系统对话

伙伴不只是「陪伴在侧」，也是**生产力协作工具**。Onboarding 完成一次性创建 5 套**系统预设对话**（固定 5 条，不可删除、不可改名），它们与用户自建的对话同级，共享同一只伙伴的角色定义、形象与长期记忆，但每次回合装载的系统提示词侧重不同：

- **陪伴**（默认）：完整角色定义 + 着装联动 + 工具教学 + 长期记忆。日常对话与情绪镜像由此预设接管；伙伴能感知用户本地时段与发言间隔，好在清晨、深夜或隔了很久再见面时自然接上。工作台的专业预设只需知道当天日期。
- **开发工程师**：抑制伴侣语气与着装联动，强调工具纪律、环境提示与技术准确性。代码评审、调试、CLI / git 工作流。
- **产品经理**：重在问题陈述、选项结构化、权衡矩阵、假设显式化。跨会话引用历史决策，故保留会话检索工具。
- **文案秘书**：语气与意图保真，默认 2–3 个变体命名意图。写作风格可作为技能沉淀，故保留技能管理工具。
- **语言老师**：双语教学导师，适配语言等级，提供字面与自然双版译文，可选练习题。

**系统预设的分离呈现**：「陪伴」预设独占生活空间作为唯一会话上下文；工作台会话列表置顶其余 4 条专业系统预设对话（开发工程师、产品经理、文案秘书、语言老师），用户自建对话与手动置顶的对话排在它们之后。系统预设对话**不可删改**，工作台新建对话亦仅提供该 4 种专业预设。所有预设共享同一只伙伴的广播伙伴属性（姓名、物种等）；切换是切换系统提示词的「当前任务人格」，而不是切换伙伴本身。

每个预设对话**独立保存消息历史**：陪伴对话与开发对话是不同上下文，避免开发长日志干扰情感陪伴的语气，反之亦然。这与定时任务临时会话、IM 渠道专属会话同处一个对话隔离模型，但目的不同——预设对话是用户主动开启的工作流切换，后两者是系统后台与外部渠道。

## 9. 记忆产品化——片刻与日记

长期记忆如果只是一堆冰冷的语义向量，对用户而言便缺乏可感知的温度与生命沉淀。SpiritAgent 将记忆体系明确分层：**底层向量记忆**专司智能检索与对话上下文注入，不对外裸露；**片刻（Moments）** 与 **日记（Diary）** 则是面向用户的生活化呈现与情感资产。

### 9.1 底层检索与叙事呈现解耦

- **底层向量记忆**：作为认知基座，随对话与交互持续沉淀事实、偏好与情感线索。它在每轮回合开始前静默前置召回，注入系统提示词供大模型思考，用户无需直接翻阅或管理复杂的向量条目。
- **生活空间叙事记忆**：在生活空间中以人类易于翻阅与共情的形态呈现。片刻是情绪瞬间的切片时间线，日记是基于自然日归集的第一人称自白。两者均由系统在后台提炼或由伙伴、用户主动记录，文风为人设第一人称口吻，而非原始检索文本。

### 9.2 生活片刻（Moments）：情绪切片时间线

生活空间的时间线中记录着高光瞬间、情绪切片与重大历程：

- **内容形态**：包含短标题、简短正文、情绪标签与可选配图（复用房间背景裁切或会话生成图），按发生时间倒序排列。
- **三类触发源**：
  1. **系统关键节点自动记录**：孵化完成后的第一句问候、衣橱换装成功、房间重新生成或重大里程碑事件自动记录，作为生活足迹。
  2. **角色主动感悟**：在日常陪伴与对话中有感而发，由伙伴主动记录（受每日配额约束，防止刷屏）。
  3. **用户随手记录**：用户在生活空间中随笔写下生活切片，伙伴将其归入时间线。
- **场景隔离不变量**：工作向系统预设会话（开发工程师、产品经理等）中仅沉淀底层工作记忆，严禁向生活空间写入生活片刻，保证生活空间的情感纯粹性。系统自动片刻同样设置每日配额上限，普通闲聊不转化为片刻。

### 9.3 第一人称日记（Diary）：自然日的心灵沉淀

日记以月历打点结合图文详情的形式呈现在生活空间：

- **自然日单篇归集**：以用户当地时区的自然日为单位，每个自然日原则上归集一篇日记。
- **夜间批处理静默提炼**：在用户休息时段的夜间维护流水线中，系统整合昨日对话摘要、底层记忆与当日片刻，由大模型以角色第一人称视角撰写一篇充满情感温度的日记。
- **用户补写与段落保护**：
  - 用户可在生活空间随时补写或编辑当天的日记。
  - 若用户已经手工编写或修改过某日日记，夜间批处理流水线绝不覆盖用户的心血，而是采取尾部追加段落的方式融入反思内容。
- **静默送达原则**：日记的生成与夜间更新不向客户端发送弹窗通知或主动气泡打扰；当用户闲暇打开生活空间的日记页时，那些静默沉淀的文字便静候阅读。
