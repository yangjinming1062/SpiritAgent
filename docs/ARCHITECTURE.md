# SpiritAgent 架构设计

> **面向人类与 Agent 的系统总览。读代码前先读本文。**

SpiritAgent 是一个**根据用户描述定制的、具有专属形象的陪伴型桌面伙伴**。用户首次安装后经一段 onboarding 对话定制伙伴的名字、性格、说话风格与外貌，系统据此生成专属桌面形象；此后伙伴常驻桌面、主动陪伴，并调用本机能力帮用户做事。

三个关键词决定一切产品与技术取舍：**定制**（形象与人格由用户定义并生成）、**陪伴**（主动、持续、有记忆的关系，而非一次性问答）、**伙伴**（交互对象是"他/她/它"，工具能力只是伙伴"会做的事"，不是产品的主角）。

**文档分层**：
- 产品设计意图（形象、动画、生命周期、onboarding、交互范式）见 [DESIGN.md](DESIGN.md)。
- 跨模块协议契约（JSON-RPC 方法 / 枚举 / 事件 / 安全 / 凭据）见 [PROTOCOL.md](PROTOCOL.md)。
- 本文聚焦**系统物理架构**——模块边界、为什么必须这样分离、通信链路的形态与权衡、跨模块不变量。
- 模块实现细节、文件树、配置项见各模块 [README.md](../README.md)（backend / client / runner / installer）。

**平台支持策略**：
- **Backend**：通过 Docker 部署，仅在 Docker (Linux 基础镜像) 内运行，**无需维护 Windows / macOS 兼容性**。
- **Runner / Desktop / Installer**：仅在 **Windows** 与 **macOS** 上原生运行。

## 1. 三模块物理解耦

系统在物理上拆分为三个核心子模块，各自承载不同职责、运行在不同环境、由不同信任域管辖：

| 层 | 所在 | 承载 | 为什么必须在物理上分离 |
|----|------|------|------------------------|
| **大脑** | Backend（云端） | LLM 编排、伙伴人格（角色定义 + 长期记忆与时刻/日记）、形象与房间资产生成、云端工具 | 伙伴的"性格与记忆"是跨设备、需多用户隔离、且依赖大模型与生图算力的核心资产，必须云端托管 |
| **手脚** | Runner（本地） | 终端、文件、浏览器、代码沙箱等本机操作能力 | 伙伴"帮用户做事"必须真正触碰用户本机；但本机操作不可上云，且执行环境必须与凭证隔离 |
| **形象与枢纽** | Client（本地） | 桌面精灵形象渲染、生活空间与工作台双入口互斥开窗管理与表面呈现、凭证持有、WS 中转、Runner 生命周期 | 伙伴要在用户桌面常驻可见、能听能说；同时是唯一可信的凭证持有点与本地/云端流量中转点 |

**核心不变量**：云端永不接触用户本机与凭证，本地 Runner 零凭证运行，Client 是唯一的可信枢纽。即便伙伴人格被 prompt 注入攻陷，最坏情况也只是受限用户账户下的本地工具被调用，不会泄露云端凭证或影响其他用户。用户**设置**（非机密部分）云端为真源、Client 持镜像（[PROTOCOL.md §2.4](PROTOCOL.md)）——云端托管的是用户偏好数据而非本机访问面，机密与设备相关节（terminal、spiritagent）仅存本机。客户端全权负责生活空间与工作台的双入口互斥开窗决策与上次入口记忆，后端零感知窗口开关与像素坐标，亦不为工作台单独生成工位背景。

伙伴的"人格"由云端持久化的**角色定义**驱动（注入每次对话的系统提示词）；伙伴的"形象"由云端生成的**形象资产**驱动（由 Client 拉取并渲染）。两者共同构成"这一个伙伴"的数字身份，归属于该用户。

## 4. 通信形态与权衡

全链路采用 **JSON-RPC 2.0** 封装双向流量。所有方法枚举、事件类型、错误信封、asset 签名见 [PROTOCOL.md](PROTOCOL.md)。

### 4.1 协议链路映射

#### A. Backend ↔ Client

单一 WebSocket 通道 /api/chat/ws（连接前现铸短时 ticket 鉴权，契约见 [PROTOCOL.md §0](PROTOCOL.md)），承载所有流式对话、控制事件、工具触发，以及形象资产下发与 onboarding 控制信令。**普通 chat / tool 类方法**见 [PROTOCOL.md §1.2](PROTOCOL.md)（清单落 backend 代码）；**伙伴生命周期专用的扩展方法**亦见 [PROTOCOL.md §1.2](PROTOCOL.md)。

#### B. Client ↔ Runner

本地 OS IPC：Windows 命名管道 / macOS UDS（0600），承载 WebSocket 帧协议。Client 充当 RPC Server，Runner 启动时主动连入；upgrade 携带每次启动生成的握手 token（校验失败回 401，握手不完成）。**选用 OS IPC + WebSocket 帧（而非 stdio 重定向）的权衡**：
1. 避免 C 库底层日志或 Python print 污染标准输入输出帧。
2. 全双工并发，按 id 异步匹配响应，避免进程读写阻塞与全局锁。
3. 零端口监听面：端点路径与 token 由 Client 单向下发，Runner 重连间重读文件以跟随 Client 重启；Windows 管道侧 token 为实际准入闸门，macOS 侧 0600 socket 为主闸门。

完整方法清单与 capabilities payload 定义见 [PROTOCOL.md §2](PROTOCOL.md)。

### 4.2 核心数据流（架构级）

#### I. 标准工具调用流（伙伴"帮忙"的底层通道）

    LLM 产出工具调用
        │
        ▼
    Backend 编排（拦截保留字段、检查迭代预算、创建调用关联）
        ▼  WS 事件下发（tool.call）
    Client 路由中转
        ▼  本地 IPC（execute_tool）
    Runner 执行（安全扫描 → 本地执行 → 脱敏清洗）
        ▼  本地 IPC 响应
    Client 捕获连接异常（Runner 离线快速失败）
        ▼  WS 回传（tool.result）
    Backend 匹配调用关联，唤醒对话协程
        ▼
    LLM 收到工具结果继续

> **产品不变量**：工具调用在用户侧以"伙伴在帮忙"的叙事呈现，原始 tool.call / tool.result 帧不直接暴露给最终用户（开发者视图除外）。

#### II. 反向 RPC 流（Runner 借大脑）

Runner 不持有云端凭证；需要模型能力的本地工具经 Client 代理转发到 Backend。链路、鉴权与速率守卫契约见 [PROTOCOL.md §3](PROTOCOL.md)。

#### III. 伙伴表达事件流（情绪 + 动画资产）

伙伴"如何表达"由 Backend 产出语义、Client 负责渲染，两者经 WS 解耦。情绪 cue 与动画资产是两条独立的流，互不阻塞：

- **inline affect**：情绪 cue 随其所属话语在同一响应帧下发，Client 无需二次猜测"这句话该配什么情绪"。
- **语义/渲染解耦**：Backend 只产出语义，渲染决策留在 Client；契约见 [PROTOCOL.md §1.4](PROTOCOL.md)，体验见 [DESIGN.md](DESIGN.md)。这条解耦使模型加载不影响语义层。

3D 模型由后端编排生成，链路、种子图与产物规则见 [docs/PIPELINE.md](docs/PIPELINE.md)；对外事件与接口契约见 [PROTOCOL.md §1](PROTOCOL.md)。

## 5. 主动陪伴与事件机制（Cron + Outbox）

**陪伴区别于工具的关键，在于伙伴会主动找用户。** 系统以 PostgreSQL LISTEN/NOTIFY + 事件 outbox 表支撑毫秒级、可水平扩展的事件分发，使伙伴的主动问候、定时提醒、情境化闲聊无需轮询即可送达：

1. **写出事件**：业务或 Cron 协程将待发送的 WS 帧写入事件 outbox 表。
2. **数据库触发器**：PostgreSQL STATEMENT 级触发器在 INSERT 时自动发出 NOTIFY。
3. **副本认领（Atomic Claim）**：每个 Backend 副本独立 LISTEN，收到唤醒后原子认领并消费该行。调度器 tick 只写入事件不 await WS 发射，避免慢客户端拖垮事务。

主动消息、Cron 定时、形象/角色变更通知等所有"伙伴主动行为"都经此通道下发。通道还承载一种**内部事件**（cron.turn.request）：调度器 tick 副本不执行自主回合（回合的流式输出、工具关联、运行时会话都是进程内状态），只写一行 outbox，由认领循环按"持有该用户 WS 的副本"路由执行。实现细节见 [backend/README.md](../backend/README.md)。

### 5.1 打扰档位约束

主动行为的档位语义与生效规则见 [DESIGN.md §6.2](DESIGN.md)；此处只锁定跨模块权威边界：

- **Client 是档位的唯一权威**：它综合用户偏好与活动上下文计算生效值，并把结果单向推给 Backend；产品规则见 [DESIGN.md §6.2](DESIGN.md)。
- **Backend 只持久化生效值**（经配置同步管道落库，[PROTOCOL.md §2.4](PROTOCOL.md)）：供服务端闸门（主动消息、cron 自主回合、情绪/空间推理入口）读取——既不独立推导，也不存储用户偏好或焦点上下文；重启不丢档位。
- **静止档在源头断流**：主动消息与主动情绪推理的入口都在后端闸门统一拦截（客户端也不发起），而非在下发端过滤；消息与情绪仍是两个独立事件通道。产品表现见 [DESIGN.md §6.2](DESIGN.md)。

### 5.2 情境化情绪

用户长时间无活动时，客户端跨过阈值时请求后端加载角色定义 + 最近记忆跑一次 LLM 推理，决定是否发出情境化情绪。**触发时机由客户端控制（知道真实 idle 状态），情绪推理由后端承担（有角色定义 + 记忆）**——各取所长，客户端不退化成规则驱动的文案池。

### 5.3 副本语义

进程内状态决定了两类进程的可扩展性不同：

- **后端 web 进程（chat 亲和，单副本语义）**：WS 连接、运行时 chat 会话、IPC 关联表都在进程内存，一个用户的对话回合必须落在持有其连接的副本上——按单副本设计部署。跨副本的部分已外置：打扰档位落库，cron 自主回合经 outbox 行路由到持连副本。
- **调度 tick 与事件认领循环**：cron 抢占走数据库 CAS、事件消费走 outbox 原子认领，均无进程内用户会话状态，可多副本运行。

### 5.4 IM 通道桥

外部 IM（微信 iLink）经 **web 进程内**的通道桥（`services/channels/`）与同一伙伴对话——与调度器同为进程内 asyncio 任务，天然满足 §5.3 的单副本语义，不需要 omp-wechat 类方案的多进程单例锁。与 cron 自主回合的路由差异是本节的关键不变量：

- **cron 回合依赖用户 WS**：调度 tick 只写 outbox 行，由持有该用户 WS 的副本认领执行（emitter 复用 WS 派发器），桌面离线即无处执行。
- **IM 回合不依赖用户 WS**：入站消息由进程内适配器接收，直接以无头 emitter 跑完整 chat 回合（桌面离线也能回），回复格式化后从原渠道送出；桌面端只读旁观 im 会话历史。面向桌面的副作用（情绪镜像、配对审批、状态变化）才走 outbox 事件。

**但两类回合中的本机工具都依赖桌面 WS**——这是上一条的必要限定，不是矛盾。回合的**语义执行**在云端（IM 侧无头即可完成），而"帮用户做事"必须触碰本机，只能经桌面这个唯一枢纽下发。因此本机工具调用不作为会话事件下发，而是按用户维度直投桌面派发器（契约见 [PROTOCOL.md §1.3](PROTOCOL.md)）：IM 与 cron 回合的会话用户永远不可能正在查看，走会话通道必被渲染端的会话闸门丢弃。这条分离使**手机成为桌面的遥控器**——IM 不只是伙伴的"另一个耳朵"，也是它的手；能力叠加在陪伴之上，不改变 IM 通道的陪伴属性。

**桌面在线是回合可见的环境事实**：IM 回合把桌面可用性（WS 在线且已同步 runner 工具，两者缺一不可）注入系统提示词，使伙伴在电脑没开机时如实告知而非含糊拒绝——离线时本机工具会被整体清出注册表，不明说则模型无从解释自己为何做不到。

每渠道一条专属 im 会话（渠道间不混流，kind 枚举与唯一外键锚定见 [PROTOCOL.md §1.7](PROTOCOL.md)）；人设/长期记忆/情感按 user 加载，与桌面回合天然共享。产品语义见 [DESIGN.md](DESIGN.md)。

## 6. 角色定义与表达层契约

Backend ↔ Client 之间的核心契约：角色定义如何驱动伙伴、形象资产如何生成与下发、情绪如何表达。**所有枚举（emotion / locale）、事件类型、asset 签名 TTL、错误信封**见 [PROTOCOL.md §1](PROTOCOL.md)。

### 6.1 角色定义（唯一真相源）

onboarding 产出的结构化角色定义持久化在 Backend 用户维度,作为系统提示词的一部分注入该用户的每次对话,驱动伙伴的说话风格、性格表现与主动行为倾向。角色定义是伙伴行为的**唯一真相源**:变更只能由用户显式发起(重新进入角色编辑),禁止 LLM 自行改写。

同一用户可在 5 套并行的系统预设对话之间切换：每套预设由常量模板与用户会话上的系统预设标识共同锚定；预设由对话服务单源管理，运行时由对话编排层统一装配，把角色定义、着装、工具指导等块按预设显式声明的子集与顺序组合进输入——伴侣人设与着装联动仅在陪伴预设生效，工作面预设（开发、产品经理、文案、语言老师）按设计意图排除不相关的伴侣噪声。系统预设对话列表置顶、不可删改。

### 6.2 形象与环境资产（跨模块契约）

伙伴的视觉与环境表达由半身像、2D 形象资产（see-through 双 provider 拆分的分层 PSD）、3D 模型以及生活空间房间背景图构成，均归属用户并在用户维度持久化。产品用途与降级体验见 [DESIGN.md §1](DESIGN.md)；资产签名与传输契约见 [PROTOCOL.md §1.5](PROTOCOL.md)；2D 拆分链与 3D 输入、供应商能力链、产物与动画映射见 [docs/PIPELINE.md](docs/PIPELINE.md)。

生活空间房间背景图将角色自然绘制进室内中远景场景，与 2D/3D 动态模型解耦；产品形态见 [DESIGN.md §1](DESIGN.md)，换装联动失效与锁保护见 [PROTOCOL.md](PROTOCOL.md)；工作台则不使用房间图。

客户端 2D 渲染级联为 **puppet（PSD 链）→ 3D → 程序化蛋**：puppet 装配失败自动落级、桌面永不空白（DESIGN §1.2 不变量）；后端拆分失败（双 provider 皆败）只置失败态，客户端经同一级联兜底。

架构约束：资产不得跨用户共享；模型与形象只在用户显式请求时再生；换装仅联动房间图与 2D 外观重建，不破坏基础身份；生成失败不得阻断客户端兜底渲染。

### 6.3 表达层契约

伙伴"说什么"由 LLM 产出，"怎么动、什么情绪"由 Client 渲染。**完整 emotion / locale 枚举、解析路径**见 [PROTOCOL.md §1.4](PROTOCOL.md)。

核心契约：
- **情绪 cue（affect）**：后端在对话响应/主动消息中携带情绪语义字段，客户端据此驱动动画状态机。emotion 枚举由 Backend 白名单与客户端情绪映射**双端对齐**，未覆盖的情绪一律按中性处理。
- **空间 cue（spatial）**：后端可附带场所语义；客户端负责把它解析为具体位置与移动方式。枚举、目标语义与协议外内部场所见 [PROTOCOL.md §1.4](PROTOCOL.md) 与 [DESIGN.md §3.2](DESIGN.md)。
- **语义与渲染解耦**：后端只产出语义，不指定渲染方式或坐标；渲染策略由客户端按产品设计与模型能力决定。这使模型加载与语义层互不阻塞。
- **affect 继承角色定义的抗注入保证**：affect 由已注入角色定义的 LLM 产出，自然符合人格；角色定义本身受保留键与不可信包裹机制保护，affect 因此继承同一保证，无需额外的情绪过滤层。
- **affect 与文本同帧；语音合成按通道分双路径**：对话响应帧内联 {文本, 情绪}，后端不下发音频。生活空间陪伴回复与会话外一次性语音（气泡朗读、音色试听、主动消息）均由客户端在文本就绪后拉取式合成——先据情绪切情绪状态、再据文本拉语音切说话状态，保证情绪基调先于语音进入。产品呈现见 [DESIGN.md §6.1](DESIGN.md)。
- **用户画像自动召回**：结构化用户字段（称呼/性别/年龄段/爱好/自由文本）在对话入口渲染成片段注入系统提示词稳定段，紧跟角色定义之后——LLM 每个 turn 都能直接看到用户身份事实，不依赖记忆工具调用。

### 6.4 行为驱动的双层模型与记忆分层

伙伴"做什么、怎么做"由两个独立来源驱动，两者不可混淆、也不可错配：

- **角色定义（静态，用户定义）→ 视觉身份与资产生成**：半身像的生图提示词从角色定义装配。换风格 = 改角色定义 → 重生半身像 + 再生纹理。3D 模型按用户显式请求重生，不随半身像重生。
- **记忆（动态，随互动累积）→ 运行时行为表达**：记忆注入 LLM 上下文，驱动**说什么、表现什么情绪、何时主动搭话、主动频率**。用户随口表达的偏好写入记忆后，LLM 在后续交互中更频繁地产出对应情绪。

**记忆分层不变量**：
- **底层向量检索记忆**（`memories` 表）：服务于相似度检索与对话上下文注入，不对外直接暴露给用户，保障长周期认知连贯。
- **生活空间叙事记忆**（`moments` 与 `diary_entries` 表）：作为面向用户的产品化呈现，记录生活情绪切片（时刻）与每日角色第一人称自白（日记）。夜间批处理静默提炼日记，且对用户编辑过的日记采取追加保护而非覆写。

**核心不变量**：记忆驱动的个性化通过**运行时行为**实现，**不通过模型重生实现**。模型只随物种变更或用户显式请求重生。这避免了"每学到一条新偏好就重生成全部模型"的不可行开销，同时让伙伴随关系深入而"表现得不一样"。

## 7. 安全与准入控制（架构原则）

**物理与凭证隔离**是安全设计的根基：

- **大脑**（云端）不接触用户本地操作系统；即便 prompt 注入攻陷伙伴人格，也在受限用户账户下执行本地工具。
- **手脚**（Runner）零 Token 运行，无法越权请求 Backend 管理级 API。
- **枢纽**（Client）是唯一持有持久用户凭证的位置；渲染与预加载进程不能接触凭证存储接口。落盘与平台机制契约见 [PROTOCOL.md §5.3](PROTOCOL.md)。
- **用户隐私数据**：角色定义与形象资产归属于该用户，按用户维度隔离。

**防御纵深（Defense Layers）**四层，完整契约见 [PROTOCOL.md §5](PROTOCOL.md)：

1. **输入清洗与指令包围**：不可信文本强制包裹、保留键防注入、角色定义防篡改。
2. **本地执行拦截**：硬阻断（系统级/凭证文件）+ 软防线（跨域写需显式许可）。
3. **动态扫描与防护**：shell 命令前置静态审查、SSRF 建连双重校验。
4. **凭据边界**：API key 永不离后端（指纹化）、自更新签名、Skills 走单独通道。

## 8. 全局开发不变量 (Invariants)

**架构层（不可破坏）：**

1. **Runner 零凭证**：Runner 进程不能被授信任何 Backend Token，所有出站/LLM 请求必须向上借道 Client 中转代理。
2. **错误遮蔽**：抛出到前端的内部错误必须脱敏；错误信封契约见 [PROTOCOL.md §1.6](PROTOCOL.md)。
3. **两阶段更新强校验**：禁止绕过 Stage 1 的预取逻辑直接覆盖本地 Runner 文件；公钥签名不匹配的升级包在 Staging 阶段直接拦截（签名契约见 [PROTOCOL.md §5.5](PROTOCOL.md)）。
4. **ID 职责分立**：会话、连接恢复与 RPC Future 使用的标识不得混用或跨生命周期复用；完整语义见 [PROTOCOL.md §6](PROTOCOL.md)。
5. **平台兼容性防御**：Windows 下进程控制或路径读取必须采用 Windows 原生封装，防止 Windows PTY 进程链悬挂（具体封装见 [runner/README.md](../runner/README.md)）。
6. **副本边界**：web 进程因运行时 chat 会话与 IPC 关联的进程内状态保持单副本语义（跨副本状态经持久化与 outbox 路由外置）。
7. **后端不下发窗口开关与工位背景**：生活空间与工作台两个入口的互斥开窗完全由客户端全权裁决，后端零感知窗口状态与像素指令，亦不为工作台单独提供工位背景。

**产品层（伙伴体验的底线）：**

8. **角色定义是伙伴行为的唯一真相源**：伙伴的所有输出风格、主动行为受持久化的角色定义约束；角色定义只能由用户显式发起变更，禁止 LLM 自行改写。
9. **形象资产归属用户**：生成的专属形象归属该用户，按用户维度隔离，不跨用户共享；形象在多次会话间保持一致，除非用户触发受控再生成。
10. **陪伴优先于工具**：产品决策发生冲突时，陪伴体验优先于工具效率。工具调用以"伙伴在帮忙"的叙事呈现，原始协议帧不直接暴露给最终用户（开发者视图除外）。
11. **伙伴表达永不空白**：任何动画状态或情绪 cue 无对应就绪资产时，客户端必须按 [DESIGN.md §1.2](DESIGN.md) 的产品兜底策略降级，用户永远不可见空白或加载态。
12. **生活空间人在画中，工作台一体伴工**：生活空间窗口内不挂载 2D/3D 模型（角色在房间背景图中呈现，桌面精灵收起）；工作台采用单一复合窗口一体化架构，左侧内嵌伴工精灵插槽，与工作台面板作为单一物理实体绑定，拖拽任意区域整体移动，工作台开启时桌面精灵收起。
13. **记忆分层产品化不变量**：面向底层语义检索的向量记忆与面向用户生活空间呈现的叙事切片（时刻与第一人称日记）严格解耦。夜间批处理静默提炼日记，不得覆写用户手动编辑内容。
14. **伙伴表达由 LLM 动态驱动**：除拖拽等机械响应外，面向用户的伙伴内容（言语、心境、心理活动、主动表达与反应）由 LLM 根据情境、记忆与即时互动推理生成并端到端透传。客户端与服务层不得用时间段分段、状态枚举映射或静态文案模板伪造这些内容。

**安全层：**

15. **LLM 工具执行边界**：后端只做 LLM 编排,不派生任何 `eval` / `exec` / subprocess / Docker 容器执行 LLM 生成的代码。3D 模型质量完全落在供应商图生3D API 上,后端仅做 SPEC 校验门。
